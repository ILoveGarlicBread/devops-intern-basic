# Backup & Disaster Recovery Architecture

This document outlines the dual-layer backup and restore architecture for the Kubernetes cluster (located in `advanced/helm_values/backup-restore`).

## Strategy Overview
The cluster utilizes a hybrid backup strategy to balance rapid infrastructure recovery (RTO) with granular data integrity.
- **AWS S3 Storage:** Both backup tools stream data securely to an AWS S3 bucket (with Wasabi cloud storage analyzed as a future terabyte-scale alternative).

## 1. Infrastructure Backups (Velero)
- **Purpose:** Snapshot-based disaster recovery for Kubernetes manifests, state, and volumes.
- **Configuration:** Scheduled to run a `daily-cluster-backup`. 
- **Storage:** Backups are deposited in the unified S3 bucket under the `velero/` prefix.
- **Use Case:** Excellent for rapidly restoring deleted namespaces, lost deployments, or destroyed PVCs. However, it risks crash inconsistency for active databases.

## 2. Logical Data Backups (Kanister)
- **Purpose:** Application-level logical backups (SQL dumps) to guarantee database integrity and allow surgical point-in-time table restores.
- **Credentials:** Uses an AWS `Profile` dynamically generated by External Secrets Operator.
- **Custom Blueprint (`mysql-blueprint.yaml`):** 
  - Kanister takes a logical dump of the Fineract MySQL databases.
  - Overcame environment restrictions by using the pre-packaged `ghcr.io/kanisterio/mysql-sidecar:0.118.0` image.
  - Bypassed `mysqldump` version mismatches with the `--column-statistics=0` flag.
  - Uses `kando` to stream compressed `.sql.gz` backups directly to AWS S3, utilizing zero local disk space during the export.

## 3. Verified Recovery Scenarios
- **Total Namespace Deletion (Cascading PVC Loss):** Successfully recovered by combining Velero (to restore the K8s StatefulSets, PVCs, and structure) and Kanister (to stream the logical `.sql.gz` data dumps back into the empty MariaDB databases). 
- **Data Corruption (Point-in-Time):** Simulated data corruption (e.g., bad client records) and performed a surgical Kanister `mysql-logical-backup` blueprint restore. Bypassed system log locking bugs by injecting the `-f` flag during MariaDB restoration.
- **Longhorn PVC Edge Cases:** Mitigated MariaDB initialization failures caused by the Longhorn `lost+found` directory during volume attachment on restoration.
